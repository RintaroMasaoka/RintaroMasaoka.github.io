# Study Note

Create study notes that let the intended reader reconstruct the central calculations and use each intermediate result. For HTML notes, use Study Note HTML Specification 1.1.0 and keep the manuscript editable as Markdown while preserving reader interactions and source references.

## Establish the project

For HTML work, read [the specification](references/specification.md) before authoring or changing the format. Inspect the project's instructions, manuscript directory, chapter registry, renderer, and publication configuration. A project may provide an implementation mapping or adapter; read it for local paths, supported features, source revisions, and legacy exceptions. Keep those project facts in the project.

Identify the published manuscript authority before editing. Older notes, source transcriptions, generated HTML, and review extracts are separate artifacts. A format-only request does not authorize rewriting the scholarly content or migrating unrelated files.

## Design and revise the explanation

For a new note or substantial change to the learning sequence, read the bundled [exposition workflow](references/exposition.md). Establish the reader's starting knowledge, the concrete operation or relation the note should teach, and the dependency from each stage to the next. Before loading unfamiliar definitions, make their local purpose intelligible. Keep the visible route sufficient for the next inference when optional details are closed.

For a prose review or broad revision, read the bundled [prose-review workflow](references/prose-review.md). Select the relevant perspectives; do not run every possible check on a small edit. Examine the whole note's argument before polishing sentences. Remove production commentary and repeated promises when they do not contribute to the reader's understanding. Preserve claims, assumptions, quantifiers, notation, and source attribution. A source or mathematical gap requires verification, not stylistic repair.

These workflows are localized from Academic Writing and are part of this skill. Do not require the separate `academic-writing` plugin for ordinary study-note work. Use a specialized scholarly workflow only when the task genuinely calls for a capability not included here.

## Create or edit a note

- Use [the manuscript example](assets/templates/chapter.md) for supported syntax and [the metadata example](assets/templates/note.config.json) for the chapter registry. Adapt examples into authored content; do not require their section structure.
- Resolve an available renderer through the project adapter. Reuse its accepted Markdown parsing, math components, preview interactions, and styles. This skill supplies the specification and authoring examples, not an executable reader. If the renderer is absent and the user requested a working site, implement and validate it within that task.
- Connect chapter metadata to navigation, routes, and page metadata. A JSON file alone does not make a legacy renderer consume it. Avoid separate editable registries for the same values.
- Audit reused reader chrome before carrying it into a new note. Keep visible labels, taglines, badges, metadata rows, and repeated titles only when they help readers identify a destination, understand their position, or perform an action. Remove template-specific copy and duplicate labels from the rendered UI; retain metadata needed for page titles and accessibility even when it is not shown. Check desktop and mobile navigation separately so a functional menu label is not mistaken for decoration.
- Keep published chapter and reference IDs stable. Use explicit passage or disclosure IDs for durable links; line-number heading anchors are only local navigation.
- Keep definitions in their original manuscript passages and preview those passages. Use disclosures and equation hints for supporting detail while preserving the premises needed in the visible reading flow.
- Run a referent-and-operation check on the visible path before accepting a passage as definition-complete. Include ordinary relational words, not just technical terms and symbols: for every role word that carries an argument (for example an input, output, remainder, correction, choice, or finite/local quantity), identify the concrete object, the operation or comparison that gives it that role, and the visible sentence or equation at or before first use that establishes both. Substitute the concrete object into the sentence. If more than one reading remains plausible, the referent first appears later, or the reader must infer an expert convention, repair the passage at first use. Check headings and chapter openings as well as prose, and rebuild the bridge at chapter transitions. Do not add glossary entries for ordinary uses whose referent and operation are already explicit in the same reading unit.
- Keep original equation numbers distinct from globally unique lookup IDs. Validate custom blocks and cross-chapter references, not only ordinary TeX.
- For mathematical exposition, run the [working-memory review](references/working-memory-review.md) on the visible reading path. Track what a reader must hold at the scale of a formula, an argument, and a chapter transition. Treat each new Latin or Greek base letter as a costly mapping unless its conventional or mnemonic association directly cues its meaning. Never introduce three or more new base letters at one transition; stage them one or two at a time. When a new symbol is unavoidable, attach its semantic noun phrase at every occurrence, with an adjacent legend for displays, until repeated use across the required reading path has made the meaning demonstrably familiar. At each completed calculation or subargument, trace downstream uses: its temporary steps are released only if subsequent reasoning uses a compact result in their place, or reconstructs a needed detail at the point of use. Reintroduce earlier results at the point of use instead of assuming the reader retained a previous chapter. Change dependencies and notation rather than adding reader-facing instructions to forget material.
- At each explanation, ask the simple question: would a visualization make this easier to understand than prose and formulas alone? Favor providing one whenever the reader would otherwise have to construct a mental picture of connections, geometry, stages, comparisons, counts, or cancellations. Place it before or beside the inference that needs that picture, even if the prose never mentions a figure. Choose a diagram, plot, table, or interactive view according to what makes the relation clearest. Show the actual objects and relations, and explain the marks and scope in nearby prose and alt text. If prose does invoke a figure or table, supply it rather than leaving the reader to imagine it; remove that reference only when the visual genuinely adds no clarity.
- Preserve figure sources and rendered assets. Check mathematical labels and readability in both themes and narrow layouts.
- Load KaTeX’s stylesheet and make every font file it references available from the note’s own build. Bundle or embed the KaTeX fonts; do not rely on another project’s development-server paths, a CDN, or an unverified fallback font. Apply the KaTeX font rules to both inline and display math without overriding them with the body font.

## Verify and deliver

For HTML notes, apply specification sections 11–12 to the changed surface. For any substantive teaching change, replay the visible reading sequence with the intended reader baseline and verify the next downstream use. Use the renderer's body extraction to review the visible reading flow separately from hidden details. For changes to definitions, derivations, structure, or the placement of premises, request an independent agent review of the extracted units before accepting the revision; the reviewer must not use later or hidden material to supply missing premises.

When a reader reports a defect, infer the reusable failure class before applying a local repair. Test analogous passages elsewhere in the note, and update the relevant skill gate when that class extends beyond the single artifact; keep one-off typos and facts local. For changed explanatory passages, make the working-memory review a separate pass after correctness and prerequisite checks. Trace each later use back to the exact earlier statement it needs. At a proposed boundary, verify that later steps depend on a compact result rather than on the intermediate chain; if a detail is needed later, retain or rederive it there. Record overload points and the dependency change used to repair them. A chain of correct, defined steps does not pass merely because a summary says the details can be set aside.

In the extracted visible body, review every explanation for a visualization opportunity, including passages that never say “figure”: name the mental picture the reader must build and decide whether supplying it would make the next inference easier. If so, provide it before the inference and verify that its marks really show the stated objects, distinctions, counts, or cancellations. A claim that invokes a figure or table also needs an adjacent, inspectable representation. Confirm each supplied asset exists in the build and is readable at narrow widths and in both themes. Separately, record a referent-and-operation ledger for each changed section: first use of a role word, its object, its operation or comparison, and the visible evidence at or before that use. Fail unresolved entries even when every symbol is defined and the calculation is correct; a build, extraction, or generic first-time-reader pass cannot certify this semantic check. Then check syntax, reference targets, metadata wiring, custom math rendering, relevant interactions, and the production build. For math typography, verify that the KaTeX stylesheet and its font assets load in development and in the built site; inspect representative inline and display formulas in the browser for the intended KaTeX glyphs and spacing. A successful TeX render or build alone does not prove that the fonts loaded. Save findings against the reviewed source revision. Existing test success is not evidence that every UI interaction or scholarly claim was checked.

Use the project's actual hosting integration and existing publication authorization. Report the delivered manuscript/site and any unsupported feature accurately. Creating this skill or a format document alone is not a publication request.

## Ownership

The generic specification, examples, and note-writing workflows belong to this skill. Consumers link to that canonical material; project adapters, manuscript registries, scholarly content, implementation mappings, and review records belong to the project. Editing a manuscript generated from an example is ordinary authoring; maintaining another writable copy of the generic specification or template is not.

When the specification changes, update its version and record compatibility changes. Projects declare their adopted version and migrate deliberately. Preserve user instructions and project publication scope.
